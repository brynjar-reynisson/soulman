# web-svc — Operational Notes

Incidents, gotchas, and decisions learned running this service — not captured in the design specs themselves (see `CLAUDE.md`'s Services section for spec links).

## SUPABASE_URL / SUPABASE_JWT_SECRET are not in this repo

Both are required environment variables (fatal startup error if either is blank), set via `.env` in each of `soulman-dev\` and `soulman-prod\` (loaded by `load-env.ps1`, same as `action-svc`'s Discord token). They must be filled in by hand before `web-svc` will start — the JWT secret is the same Supabase project secret `agent-suite`'s backend already uses (`supabase.jwt-secret` in its `application.yml`), since both apps verify tokens from the same hosted Supabase project.

## Owner-email check, not a roles table

Unlike `agent-suite`'s `UserResolverFilter` (DB-backed `suite_user`/`user_role` lookup), `web-svc`'s `auth.Verifier` does no database lookup at all — it just compares the JWT's `email` claim against `web.owner_email` in `config/dev.json`/`prod.json`. This is deliberate: Soulman has exactly one real user. If this ever needs multiple authorized users, that's a real design change, not a config tweak.

## `/api/status` never fails even when a downstream service is down

Each of the four downstream `/health` checks in `apiStatus` has its own 5s timeout and failures are captured per-service (`"down"` in the response map) rather than failing the whole request — a single service being down (e.g. during a rebuild) shouldn't take down the dashboard's status panel along with it.

## `/api/system-monitor` is a plain proxy, not a status aggregator

Unlike `/api/status` (which independently probes 4 services' `/health` endpoints and reports up/down), `/api/system-monitor` (added 2026-07-20) is a thin passthrough of `perception-svc`'s `GET /api/system-monitor/status` via the existing `proxyGet` helper — same pattern as `/api/episodes`/`/api/raw-inputs/recent`. The data's freshness is entirely `perception-svc`'s: whatever its `sysmonitor.Watcher` last polled (up to 5 minutes stale), not re-checked by `web-svc` on each dashboard load.

## `SUPABASE_JWT_SECRET` is optional, not required

`web-svc/config/config.go`'s `Load()` used to treat a blank `SUPABASE_JWT_SECRET` as a fatal startup error, alongside `SUPABASE_URL`. That was wrong and has been fixed: this deployment's hosted Supabase project signs auth tokens with ES256 (asymmetric, verified via its JWKS endpoint — see `web-svc/auth/verifier.go`), not the legacy HS256 shared-secret scheme, a conclusion reinforced by `agent-suite` having run against this same Supabase project for a while without ever setting `SUPABASE_JWT_SECRET`/`SUPABASE_PROD_JWT_SECRET` anywhere. `Load()` now defaults `SUPABASE_JWT_SECRET` to an empty string via `env("SUPABASE_JWT_SECRET", "")` rather than erroring.

A blank value does not mean "HS256 tokens simply fail verification against a mismatched secret" — that phrasing (from an earlier version of this note) was wrong and described a real auth-bypass vulnerability rather than a benign failure mode: HMAC-SHA256 with a zero-length key is a fully well-defined, computable operation, so a forged HS256 token signed with an empty key would have verified successfully against an empty `v.jwtSecret`, letting an attacker self-sign arbitrary claims (including the `email` claim the owner check relies on) with no knowledge of any real secret. The actual, correct behavior (fixed in `web-svc/auth/verifier.go`'s `Verify` keyfunc) is that an empty/unconfigured `jwtSecret` makes the HS256 branch refuse to verify *any* HS256 token outright, before ever attempting HMAC verification — it returns an error from the keyfunc rather than a key, which `ParseWithClaims` maps to `Unauthorized`. So an unset secret narrows accepted tokens to ES256/JWKS only; it does not "fail closed on a per-token basis," it excludes the entire algorithm. `SUPABASE_URL` remains fatal-if-blank, since ES256 verification depends on it to build both the JWKS URL and the expected issuer.

## `auth.Verifier`'s JWKS cache never refreshes or refetches on an unknown `kid`

`getOrFetchPublicKey` (`web-svc/auth/verifier.go`) caches EC public keys by `kid` after fetching Supabase's JWKS endpoint, but if a token arrives with a `kid` the cache doesn't recognize, it silently falls back to the first-seen key instead of refetching the JWKS document. This was flagged as a residual gap in Task 2's code review and deliberately left unfixed there as out of scope. In practice this means: if Supabase ever rotates its signing key, tokens signed with the new key will carry a new `kid`, the cache (populated before rotation) won't have it, and verification will keep retrying the stale pre-rotation key rather than fetching the new one — so newly issued tokens would fail verification until the process is restarted (which repopulates the cache from a fresh JWKS fetch). A restart is currently the only way to pick up a rotated key; there is no TTL or unknown-`kid` refetch trigger.

## `reports.Read` now combines two files, not one (added 2026-07-20)

See `docs/superpowers/specs/2026-07-20-daily-report-importance-split-design.md`. `reports.PathForDate` gained an `important bool` parameter and `reports.Read`'s return value changed from one file's raw bytes to a combined `## Important` / `## Not Important` string — `web-svc/httpserver/reports_handler.go` needed no changes at all, since it only calls `reports.Read` and forwards `content` through unchanged.

## Dashboard is tunneled to `soulman.breynisson.org` (prod only, added 2026-07-21)

`cloudflared` maps `https://soulman.breynisson.org` to prod's Vite preview server on `localhost:5191`. Two things had to change for this to work, both prod-only (dev is never tunneled):

1. `web/vite.config.ts`'s `preview.allowedHosts` must list `soulman.breynisson.org` — Vite's preview server rejects requests whose `Host` header isn't localhost or in this allowlist (`Blocked request. This host is not allowed.`). This file lives in the vault and is mirrored by `run-web.ps1`'s robocopy into both `soulman-dev\web\` and `soulman-prod\web\`, so the allowlist applies to both environments' preview servers even though only prod is actually tunneled.
2. `soulman-prod\web\.env`'s `VITE_AUTH_REDIRECT_URL` must be `https://soulman.breynisson.org` (was `http://localhost:5191`), and that same URL must be added to the Supabase project's Auth > URL Configuration > Redirect URLs allowlist — otherwise Google OAuth completes but Supabase refuses to redirect back to the tunneled origin. `soulman-prod\web\.env` is excluded from the robocopy mirror (see `run-web.ps1`'s `/XF .env*`), so it's edited directly in `soulman-prod\` rather than in the vault. Since `VITE_*` vars are inlined at build time, a rebuild (`npm run build`) of prod's `web` is required after changing it — restarting the service via `run-web.ps1` (or the next `start-everything.ps1` login run) picks it up.

A third change was needed and easy to miss because it fails silently: `config/prod.json`'s `web.cors_allowed_origin` (`web-svc/httpserver/server.go`'s `cors.Handler`) was still the `http://localhost:5191` placeholder noted as such in `docs/superpowers/specs/2026-07-19-soulman-web-dashboard-design.md`. Once the dashboard is loaded from `https://soulman.breynisson.org`, every browser fetch to `web-svc` (still `http://localhost:9005` — same machine, so it reaches web-svc fine) carries that as its `Origin`, which the stale allowlist rejects; the browser then blocks the response with no CORS header rather than surfacing a clean error. `web/src/App.tsx`'s effect only special-cases a 403 `ApiError` (→ "restricted" screen) — any other failure, including this one, falls through to `setView('login')`, so the symptom looks like sign-in silently failing and looping back to the Google button, with no visible error at all. Fixed by setting `cors_allowed_origin` to `https://soulman.breynisson.org`; `web-svc` reads it from `config.json` at startup (copied from `config/prod.json` by `run-web-svc.ps1`), so a `web-svc` restart is required after changing it.

Separately, loading the dashboard from a public origin while `web-svc`/other services still listen on `localhost` also triggered Chrome/Edge's Local Network Access prompt ("this site wants to access other apps and services on this device") on first load — an unrelated browser permission gate (public page → local-network target) introduced in Chrome 141+, not a Soulman bug in itself, but a symptom of the design flaw fixed below.

## `web/src/api.ts` called `http://localhost:9005` directly - broke on any device but the host (fixed 2026-07-21)

The CORS fix above made sign-in work again *on the machine running the services*, but a second machine hit the identical symptom (silent bounce back to the Google sign-in screen). Root cause: `VITE_WEB_SVC_URL` was baked in as an absolute `http://localhost:9005` (`9015` in dev), evaluated by the *browser*, not the server. On the host machine that happens to reach `web-svc` because "localhost" resolves to the same box. From any other device, "localhost" resolves to that device itself — nothing is listening there, the fetch fails, and it hits the same unqualified `else → setView('login')` in `App.tsx` as the CORS bug did. Cloudflare only tunnels the frontend (`soulman.breynisson.org` → `localhost:5191`); `web-svc` itself is not reachable from outside the host at all, and the fix does not expose it either.

`digital-me` and `agent-suite`'s frontends (`IdeaProjects/digital-me/frontend/vite.config.ts`, `IdeaProjects/agent-suite/frontend/vite.config.ts`) already solve this the standard Vite way: a `proxy` entry on `server`/`preview` that forwards specific path prefixes to the local backend. Vite's own process runs on the same machine as the backend, so *its* proxied request to `localhost` is legitimate — only the browser-facing side is same-origin. Applied the same pattern here: `web/vite.config.ts`'s `server.proxy` and `preview.proxy` each forward `/api` to the environment's `web-svc` port (`9015` dev, `9005` prod), and `web/src/api.ts` now calls relative paths (`fetch(path, ...)`) instead of prefixing an absolute `WEB_SVC_URL` — the browser only ever talks to whatever origin served the page. `VITE_WEB_SVC_URL` is gone from `.env.example` and both environments' `.env` files as a result. This also means the Local Network Access prompt above no longer fires for the dashboard: the browser never sees a `localhost` target again, Vite's preview server does that hop server-side.

## Leveled logging (log/slog, added 2026-07-27)

The five `log.Printf`/`log.Fatalf` call sites in `main.go` replaced with stdlib `log/slog` (`slog.Error`/`slog.Warn`/`slog.Info`) — no new dependency. `web-svc` has no background retry/degraded-fallback logic of its own (unlike the other four services), so the reclassification here is simple: config-load and HTTP `ListenAndServe` failures are `slog.Error`, started/listening/shutting-down messages are `slog.Info`. The startup `log.Fatalf` became `slog.Error(...)` followed by an explicit `os.Exit(1)`.

## Known gap: dashboard doesn't surface degraded/internal_health status (as of 2026-07-27)

The dependency-health feature (`docs/superpowers/specs/2026-07-27-dependency-health-design.md`) lets a service report `"status":"degraded"` from `/health` while still returning HTTP 200 (the process is fine; a dependency inside it isn't) — but `/api/status`'s aggregator (`httpserver/server.go`) only checks each service's HTTP status code, so a degraded memory-svc still shows "up" on the dashboard. Separately, `web/src/components/StatusPanel.tsx` filters system-monitor rows to `service_health` plus a fixed resource-type list, so the `internal_health` rows perception-svc already records (including per-dependency detail, e.g. `memory-svc:postgres`) never reach the UI even though `/api/system-monitor/status` already serves them. Discord notification — this feature's primary detection goal — is unaffected and works correctly. Surfacing degraded status and `internal_health` rows on the dashboard is real remaining scope, deferred to a follow-up design (deciding whether `/api/status` should parse `/health` response bodies is a contract change touching all five services, not a quick patch).

## Obsidian file viewer/editor (added 2026-08-07)

See `docs/superpowers/specs/2026-08-07-obsidian-file-viewer-design.md`. `web.obsidian_root` is a new required shared-config field (fatal startup error if blank, same "every `web.*` field is required" convention as the other five) — both `config/dev.json` and `config/prod.json` point it at the same literal path, `C:\Users\Lenovo\Documents\obsidian`, since this isn't a per-environment resource. The new `web-svc/obsidian` package validates every `folder`/`file`/`new_name` argument against path traversal (rejects `..`, `/`, `\`, and — after a final-review fix — `:`, via `filepath.IsLocal`) before touching the filesystem, since this is the first write-capable surface on `web-svc` and prod's dashboard is reachable through a public `cloudflared` tunnel. `ListFolders`/`ListFiles` return `[]string{}` rather than a nil slice specifically so empty results serialize as JSON `[]`, not `null` — an uninitialized `var folders []string` (or `var files []string`) marshals to `null`, which the frontend's `data.files === null` loading check would render as a permanent "Loading..." spinner instead of the "No files" empty state; both `ObsidianFileList.tsx` and `ObsidianFolderList.tsx` also defensively guard with `?? []` on the response in case any other caller ever hits this. A newly created file opens directly in `ObsidianFileEditor` (not the read-only viewer) via `ObsidianFileViewer`'s `initialMode` prop, tracked by `ObsidianFileList`'s `justCreated` state — this was a late fix after the final review caught that the shipped behavior silently dropped the approved spec's "auto-selected in edit mode" requirement.

### Navigation state didn't survive reload (fixed 2026-08-08)

Real-world bug reported from mobile use: the page, expanded folder, selected file, and edit/view mode all lived only in React `useState` with nothing backing it, so a reload — which mobile browsers routinely trigger after the screen turns back on or after switching apps — always restarted the whole tree cold, landing back on the dashboard even mid-read or mid-edit. Fixed by mirroring that state into the URL query string (`?page=obsidian&folder=...&file=...&mode=edit`) via `history.replaceState`, in a small `web/src/urlState.ts` helper (`getParam`/`setParams`) rather than pulling in a router library — the app has exactly two top-level views and didn't need one. Each component seeds its initial state from the URL via a lazy `useState` initializer and writes back to it on the relevant user action (`App.tsx` on page switch, `ObsidianFolderList` on expand/collapse, `ObsidianFileList` on select/create/rename, `ObsidianFileViewer` on edit/save/cancel). This does not persist unsaved edit-mode draft text — a forced reload mid-edit still loses in-progress changes, since the file's real content is re-fetched from disk on restore; only *which* file is open and in what mode survives. Draft autosave would be a separate, larger feature.

## Claude remote-session launcher (added 2026-08-09)

See `docs/superpowers/specs/2026-08-09-claude-remote-sessions-design.md`. The new `web-svc/claudesession` package is deliberately fire-and-forget: `Launch` calls `cmd.Process.Release()` immediately after a successful `Start()`, so web-svc holds no handle on the spawned `claude --remote-control` process and cannot report anything about it after the initial launch — session lifecycle is entirely owned by Claude Code's own remote-control registration (`claude.ai/code`). `web.claude_project_roots` (three curated `{label, path}` entries: Obsidian, IdeaProjects, Misc Projects) is required to be non-empty at config load, unlike `obsidian_root` its individual `path` values are *not* required to exist on disk — `claudesession.ListRoots` reports a missing root as `exists: false` per-request instead, since these are ordinary project folders that can come and go, unlike the Obsidian vault.

**Automated tests never exercise the actual process-spawn success path.** `claudesession_test.go` and `claude_handler_test.go` only cover validation errors (empty session name, invalid folder segment, missing folder) — every one of those returns before `Launch` reaches `exec.Command(...).Start()`. A test that combined a valid folder with a valid session name would genuinely spawn a `claude --remote-control` process on whatever machine runs `go test`, which is never acceptable in an automated suite. If this package is extended later, preserve that boundary rather than adding a "happy path" test.

Windows process detachment (`claudesession_windows.go`, `//go:build windows`, `syscall.CREATE_NEW_PROCESS_GROUP`) follows the same filename-suffix convention as `perception-svc/sysmonitor/stats_windows.go` — no non-Windows counterpart exists because every Soulman service only ever runs on Windows.

Manual verification of the launch path (a real `claude --remote-control` process actually appearing) was deliberately deferred rather than triggered from an agent session — spawning one is a visible, persistent side effect (another background Claude Code session on the machine), not a reversible file edit, and belongs to the user's own click-through once this is merged and running for real. What *was* verified pre-merge: built `web-svc` directly from this feature branch into an isolated scratch directory (temp dir, temp port, never touching the real `soulman-dev`/`soulman-prod` processes or `.env`), confirmed it starts with no fatal config error (proving `claude_project_roots` parses from `config/dev.json`) and that both `/api/claude/roots` and `/api/claude/launch` are registered behind auth (401 with no token, matching the httptest-level coverage). See `~/.claude/skills/deploy-soulman-services` for why a live rebuild against the real dev/prod environments is never done by hand-rolling a copy/robocopy command outside their `run-<svc>.ps1` launchers.

### Missing `--bg` flag meant every real launch silently died (fixed 2026-08-09)

Exactly the residual risk flagged by this feature's final code review, confirmed on the first real click-through: the user launched a session against `IdeaProjects/old-laptop`, the dashboard reported success (the `204` from `POST /api/claude/launch` only ever confirms `cmd.Start()` succeeded — the OS created the process), but no `claude` process was running seconds later, nothing showed up in `claude agents` or on the tablet, and — because `Launch` deliberately discards the child's stdout/stderr as part of the fire-and-forget design — nothing was logged anywhere either. `web-svc-startup-err.log` was checked and was clean, which was itself the tell: a genuinely broken `cmd.Start()` would have logged via the `slog.Error` added earlier the same day; a process that starts and exits cleanly on its own logs nothing.

Root cause, found by reproducing the exact command by hand (`cd <folder>; claude --remote-control --name "<session>"`, taken directly from the `Launch` call site): without `--bg`, `claude --remote-control` runs as a normal **interactive foreground session** expecting a real terminal to attach to. `Launch` gives the child `nil` `Stdin`/`Stdout`/`Stderr` (all three become the null device), since it's fire-and-forget by design and was never meant to interact with the process at all. With no terminal to attach to, the plain command exits immediately and silently — no crash, no error, just a process that starts and stops within milliseconds, invisible to `CREATE_NEW_PROCESS_GROUP` and invisible to `Get-Process claude` a moment later. Confirmed independently by running the reproduced command by hand: the plain form opened a normal interactive session (as expected — a real terminal was attached); adding `--bg` made it start detached, which is what `Launch` needs.

Fix: `Launch` now runs `claude --remote-control --bg --name sessionName` (`web-svc/claudesession/claudesession.go`). No test covers this directly — same boundary as above, verifying the success path means actually spawning a session. This is a real remaining gap: nothing in the automated suite would catch a *third* wrong invocation shape if `claude`'s CLI ever changes again; the only signal is another silent no-op on the next live click-through.

## File browser (added 2026-08-19)

See `docs/superpowers/specs/2026-08-19-file-browser-design.md`. `web-svc/filebrowser` takes the same validated-path shape `obsidian` already uses (reject `..`, `/`, `\`, `filepath.IsLocal`, then a `filepath.Rel`-based defense-in-depth `isWithin` check against the root) and extends it from a single path segment to arbitrary depth: `relPath` is split on `/` and every resulting segment is run through `validSegment` individually, before any segment is joined onto `root.Path` — checking only the fully-joined string would miss a traversal attempt hiding in one otherwise-legal-looking segment. This had to change because unlike Obsidian's one-level-deep browsing (and the Claude launcher's single project-folder pick), the file browser drills into arbitrary subfolders.

`filebrowser.RootListing` deliberately has no `Folders` field, unlike `claudesession.RootListing`. Claude's root listing preloads each root's project folders up front because it's a shallow, bounded list picked once per launch. File-browser navigation can't do that — at arbitrary depth there's no bounded "list everything" step that would make sense to preload — so it stays stateless per request: every navigation, including the very first click into a root, is its own `List` call.

No extension filtering anywhere in this feature — the one deliberate difference from `obsidian`'s `.txt`/`.md` gate. "Any file" (photos, PDFs, archives) is the whole point of this feature, per the spec's Goals.

The 200MB upload cap (`maxUploadBytes` in `web-svc/httpserver/files_handler.go`) is a hardcoded `const`, not part of the shared config schema. This is a deliberate YAGNI call, same posture as Obsidian's uncapped notes: start with *some* cap (unlike Obsidian, since this accepts arbitrary binary uploads on a publicly-tunneled endpoint) but don't build config plumbing for a number that's only a guess — bump it in code if 200MB turns out to be wrong.

A final-review finding, fixed as part of landing this feature rather than deferred: `FileRootList` rendered `<FileBrowser root={selectedRoot} />` with no `key`. Since `root` is the only prop that changes when the user picks a different root, React reused the same `FileBrowser` instance across the switch, and its internal `currentPath` state — possibly drilled several folders deep under the *previous* root — survived into the new root, producing a 404/"Unable to load folder" and a broken breadcrumb. Fixed with `key={selectedRoot}`, forcing React to unmount and remount `FileBrowser` on every root switch so `currentPath`'s lazy `useState` initializer re-runs against the fresh root.

## File sharing — time-limited links (added 2026-08-19)

See `docs/superpowers/specs/2026-08-19-file-sharing-design.md`. `web-svc/sharelink` tokens are stateless by design: `base64url(JSON payload)` + `.` + `base64url(HMAC-SHA256 over that payload text)`, carrying `(root label, relative path, filename, exp)`. Nothing is written down when a link is issued and nothing is looked up when one is opened — which is the point, because `web-svc` has no database and no session store of its own (it proxies `memory-svc` for everything persistent), and adding one just to track share links would have been the single biggest structural change this small feature could make. The cost is spelled out in the spec's Non-Goals and is real: no revocation before expiry, and no single-use enforcement — a link is live for its whole TTL (`web.share_link_ttl_minutes`, 60 by default) to anyone holding it.

The signing secret is 32 `crypto/rand` bytes generated in `main.go` at every process start, held only in memory — deliberately *not* an `.env` value. So a redeploy, or a `start-everything.ps1` run at the next login, invalidates every outstanding link regardless of its TTL; those tokens then fail signature verification and produce the same generic 404 as a tampered one, since the server genuinely can't tell the two apart. Accepted tradeoff: it avoids a new secret to provision in two environments, and restarts are rare relative to a 1-hour TTL.

`GET /dl/{token}` is the only route in this service that isn't behind the owner-JWT group — every other endpoint, including `POST /api/files/share` which *issues* the tokens, stays inside it. That's the whole feature (the recipient has no Supabase login), but it means the token is a bearer capability: whoever holds the URL gets the file, and nothing else is checked. `filebrowser.ResolveFile` still runs on the decoded path, so a token can only ever name a file inside a configured `web.file_browser_roots` entry.

### Share tokens were being written into the request log (final-review finding, fixed before merge)

Caught in this branch's final whole-branch review, not in production, but it would have been a slow leak: `buildRouter` applied chi's `middleware.Logger` at the top of the router, which logs every request's full path. For `/dl/{token}` the path *is* the credential, so every share link opened appended a live, unexpired token verbatim to `logs/web-svc-startup.log` — a file that is never rotated and that gets pasted around during debugging (see `memory-svc/NOTES.md` for how large those logs get before anyone notices).

The fix is `requestLogger` in `server.go`: a dispatcher middleware that sends `/dl/`-prefixed requests through a small `log/slog` middleware logging `method`/`status`/`bytes`/`duration` against the literal `/dl/<redacted>`, and everything else through chi's `middleware.Logger` exactly as before. Dropping the log line entirely was rejected — that would have created a blind spot on the one unauthenticated route.

Worth knowing if this is ever touched: the redaction *has* to be a routing decision made ahead of chi's logger, not a rewrite of the path. `middleware.RequestLogger` snapshots the request path into its log entry before calling the next handler, so there's no later hook that changes what it prints; and redacting by mutating `r.URL.Path` in an earlier middleware would make chi route on the placeholder, handing `shareDownload` a `chi.URLParam(r, "token")` of `<redacted>` instead of the real token. `TestShareDownload_RequestLogNeverContainsTheToken` (issue a real token, hit the route, assert the captured `slog` output contains `/dl/<redacted>` and never the token) is the regression guard.
